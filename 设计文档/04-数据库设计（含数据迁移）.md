## 一、功能变化说明

> 面向非技术人员：数据库的"感受"完全没有变化。产品数据、分类、询价、B2B 密码——存的东西一模一样，查的方式不同但结果相同。

### 对比

| 维度 | 老版 v3.0（Prisma + PostgreSQL Docker） | 新版（Drizzle + Neon Serverless） | 变化感受 |
|:-----|:-----|:-----|:-----|
| 数据库类型 | PostgreSQL | **PostgreSQL（Neon 云端托管）** | 一样是 PostgreSQL，用法不变 |
| 表数量 | 33 张 | **33 张** | 表结构完全一致 |
| ORM 工具 | Prisma | **Drizzle** | 后台操作感觉不到，只有开发者写代码时语法不同 |
| 连接方式 | TCP 直连（需要 Docker 网络） | **HTTP 连接（Neon 的 Serverless 驱动）** | 后台操作感觉不到 |
| 备份恢复 | 手动 pg_dump + 服务器文件 | **Neon 自带 6 小时时间点恢复 + R2 冷备兜底** | 恢复更快，管理员可自行操作 |
| 表定义语言 | Prisma Schema（.prisma 文件） | **Drizzle Schema（.ts 文件）** | 对非技术人员透明 |

## 二、管理规则说明

> ⚠️ 本节给管理员和操作人员看——哪些事能做、哪些事绝对不能做、出了问题找谁。

### 2.1 数据权限

| 数据类型 | 谁能看 | 谁能改 | 谁能删 |
|:-----|:-----|:-----|:-----|
| 产品数据 | 全部员工 | admin / editor | admin / editor |
| 分类结构 | 全部员工 | admin / editor | admin（删除需二次确认） |
| B2B 展示区密码 | admin（二次验证后才能看明文） | admin | admin |
| 客户询价记录 | 全部员工 | admin / customer_service（仅状态） | admin |
| 聊天消息 | 全部员工 | 不可修改（只能追加） | admin |
| 样品申请 | 全部员工 | admin / customer_service（仅状态+物流） | admin |
| 员工账号 | admin | admin | admin（不能删最后一个 admin） |
| 操作日志 | admin | 不可修改 | 不可删除（系统自动清理 1000 条旧记录） |

### 2.2 绝对不能做的事

1. **不要手动在数据库里改数据**——所有操作必须通过后台页面完成
2. **不要删除"00 未分类"**——这是系统的安全阀，有产品没分类时会自动归到这里
3. **不要把 B2B 密码明文发给不相关的人**——查看密码后及时关闭弹窗
4. **修改 B2B 密码后，通知所有相关客户**——旧密码 24 小时内还能用

### 2.3 出了问题找谁

| 问题 | 联系人 |
|:-----|:-----|
| 数据库连不上（后台报错） | 开发人员 |
| 误删了数据 | 管理员用 Neon 控制台做时间点恢复 |
| B2B 密码忘了 | admin 在后台展示区管理里查看 |
| 图片丢了 | 检查 R2 存储桶，联系开发人员 |

## 三、常见问题自查

### Q1：产品删了但数据还在？
- A：删除产品确实会从数据库移除。如果后悔了，需要管理员通过 Neon 的时间点恢复功能恢复到删除之前。所以删产品前请再三确认。

### Q2：数据库满了怎么办？
- A：Neon 免费套餐 0.5GB 存储。33 张表结构化数据一般占不到 200MB。主要是产品图片和视频占空间，但图片视频存在 R2 里不在 Neon 里，不占用数据库空间。

### Q3：B2B 密码修改后客户还能用旧密码？
- A：是的，已获得 token 的客户 24 小时内仍可用旧密码。这是为了方便客户，避免正在浏览时突然被踢出去。24 小时后 token 过期，只能用新密码。

### Q4：能找回某个时间点的数据吗？
- A：能。Neon 免费套餐支持 6 小时内的任意时间点恢复。超过 6 小时可以通过 R2 里的每日冷备文件恢复（联系开发人员操作）。

## 四、存储架构变更

> 老版的数据全部存在一个 PostgreSQL 里。新版拆成三层：

### 4.1 三层存储分工

```
┌─────────────────────────────────────────────────────┐
│  Neon Serverless PostgreSQL（主数据库）               │
│                                                     │
│  33 张业务表，所有核心数据在这里：                       │
│  · 用户、分类、产品、B2B 展示区分类、展示区产品关联       │
│  · 询价、询价明细、聊天消息、样品申请                    │
│  · 产品翻译、展示区翻译、产品图片、产品视频               │
│  · 客户评价、首页配置、导航、社交媒体、页面内容            │
│  · 网站设置、SEO 设置、搜索关键词                       │
│  · 操作日志、文件上传记录、产品推荐关系                   │
│  · 产品布局、浏览日志、GDPR 同意记录                     │
│  · B2B 访问 Token                                    │
│                                                     │
│  特点：支持复杂查询、关联查询、事务保护                    │
├─────────────────────────────────────────────────────┤
│  Cloudflare KV（高速缓存）                             │
│                                                     │
│  · 会话数据（auth_token → user 信息映射）               │
│  · API 限流计数（按 IP 的请求频率）                      │
│  · B2B 24 小时访问 token（按分类缓存验证结果）            │
│  · 热点分类数据和产品列表缓存                            │
│  · IP → 语言缓存                                      │
│                                                     │
│  特点：全球同步、边缘低延迟、自动过期                       │
├─────────────────────────────────────────────────────┤
│  Cloudflare D1（轻量数据库 — 仅分析快照）                 │
│                                                     │
│  · 浏览统计按天/国家/来源的汇总数据（只读快照）              │
│  · 每天由 Cron 定时从 Neon 汇总 SQL 写入 D1（只写一次）     │
│  · 后台分析页面查 D1 快照，不消耗 Neon 计算资源              │
│                                                     │
│  特点：Workers 原生访问、SQLite 兼容语法                   │
│                                                     │
│  ⚠️ 不再存：站点配置（→ Neon）、GDPR记录（→ Neon）         │
│     Neon 是唯一的真实数据源，D1 是只读快照                  │
└─────────────────────────────────────────────────────┘
```

> 📝 施工中变更：KV 实际不存会话数据——登录态采用无状态 JWT（httpOnly Cookie，jose 签发校验，1 小时有效期），KV 实际存限流计数、B2B token 与首页配置缓存；D1 的分析快照定时汇总（Cron）尚未落地，当前浏览分析直接查 Neon（product_view_logs 表）

### 4.2 为什么分开存？

| 理由 | 说明 |
|:-----|:-----|
| **性能** | 高频读写的缓存数据放 KV，不占用主库连接，全球延迟更低 |
| **成本** | 分析汇总数据放 D1 只读快照，后台分析页不消耗 Neon 计算资源 |
| **架构清晰** | 各层职责明确，出问题时能快速定位是哪一层的问题 |
| **平滑扩展** | 后期流量大了，主库压力只来自核心业务查询，缓存和配置独立扩展 |

## 七、关键数据规则

### 7.1 分类规则
- 无限层级，parentId 自引用
- 父分类不直接存产品，仅末级（叶子）分类可存产品
- "00 未分类" isProtected=true，不可删除
- 同级名称不可重复
- 删除分类时产品自动移入"00 未分类"

### 7.2 产品规则
- categoryId 必须指向末级分类或"00 未分类"
- slug 全局唯一，自动生成（基于中文名转拼音+唯一后缀）
- 描述和冲泡指南存在 productTranslations（6 语言）或 showcaseTranslations（展示区额外语言）
- 推荐产品最多 3 个

### 7.3 B2B 展示区规则

| 规则 | 说明 |
|:-----|:-----|
| 分类树独立 | showcase_categories 完全独立于 categories，两棵树互不干扰 |
| 密码独立 | 每个 B2B 分类有独立 AES 加密密码 |
| 密码管理 | 仅 admin 可查看明文（需二次验证），editor 不可操作 |
| 多对多产品关联 | 通过 showcase_products 表，一个产品可属于多个 B2B 分类 |
| 24 小时 Token | 密码验证成功后签发 token，有效期 24 小时 |
| 密码错误锁定 | 同一 IP 连续输错 5 次锁定 30 分钟（KV 计数） |
| 展示区默认语言 | showcaseLocale 存在关联表中，不同分类可有不同默认语言 |

### 7.4 聊天消息规则

| 规则 | 说明 |
|:-----|:-----|
| 消息归属 | 每条消息属于一个询价（inquiries） |
| 发送者类型 | customer（客户）= 前台留言；staff（员工）= 后台回复 |
| 附件 | 支持图片附件（R2 存储，URL 写入 attachment 字段） |
| 已读状态 | 员工发送的消息追踪客户是否已读 |
| 实时性 | 一期用轮询（15 秒），二期升级 Durable Objects |

### 7.5 认证规则
- 后台密码使用 Web Crypto API SHA-256 哈希存储
- 连续输错 5 次锁定 15 分钟
- JWT token 有效期 1 小时
- 后台 1 小时无操作自动退出（前端 Hook + 后端检查）

### 7.6 操作日志规则
- 所有增删改操作 + 登录/登出 + 配置修改 + B2B 密码变更都记录
- 保留最近 1000 条
- 只追加、不修改、不删除

## 九、老数据迁移方案

> ⚠️ 本方案的目标：把老版 yiquantea.cn 网站的所有数据，完整迁移到新版 yiquantea.com，不丢一条数据，上线当天无缝切换。
>
> 📝 施工中变更（实际执行情况）：分类树已于阶段 18 迁移（老版 seed-categories.ts 46 节点，合并后 49）；产品 14 款 + 6 语言翻译 84 条已种子入库；B2B 2 分类与员工 4 账号已种子创建；老版产品图片未批量上传 R2（当前用本地 SVG 占位图，上线前替换）；老版询价记录无存量未迁移；评价为种子新建 5 条非老版迁移

### 9.1 迁移范围

| 数据类型 | 数据量（预估） | 迁移难度 | 迁移方式 |
|:-----|:-----|:-----|:-----|
| 产品数据（含图片 URL） | ~150 条 | 低 | 写脚本导出 JSON → 导入新版 |
| 产品图片文件 | ~1 GB | 中 | R2 批量上传 |
| 分类树 | ~47-165 个节点 | 低 | 导出 JSON → 按层级插入新版 |
| B2B 展示区分类 + 密码 | 2 个分类 | 低 | 手动在新版创建（密码需重新加密） |
| 询价记录 | 视数据量 | 低 | 导出 JSON → 批量插入 |
| 客户评价 | ~10 条 | 低 | 导出 JSON → 批量插入 |
| 首页配置、导航、SEO | 少量 | 低 | 手动在新版配置（量少，手动更稳） |
| 网站设置、社交媒体 | 少量 | 低 | 手动在新版配置 |
| 员工账号 | 少量 | 低 | 手动创建（密码需重新设置） |
| 操作日志 | 不限 | — | **不迁移**（老日志没必要带过去） |

4. 准备一个临时脚本目录 `migration/`

const prisma = new PrismaClient();

async function exportProducts() {

}

导入脚本的核心逻辑（以产品为例）：

```typescript
// migration/import-products.ts
import 'dotenv/config';
import { drizzle } from 'drizzle-orm/neon-http';
import { neon } from '@neondatabase/serverless';
import * as schema from '../src/drizzle/schema';
import products from './data/products.json';
import imageMap from './data/image-url-map.json';

const sql = neon(process.env.DATABASE_URL!);
const db = drizzle(sql, { schema });

async function importProducts() {
  const urlMap = new Map(Object.entries(imageMap));

  for (const p of products) {
    // 1. 创建产品主记录
    await db.insert(schema.products).values({
      sku: p.sku,
      nameZh: p.nameZh,
      nameEn: p.nameEn,
      slug: p.slug,
      categoryId: p.categoryId,
      priceCNY: p.priceCNY,
      priceUSD: p.priceUSD,
      spec: p.spec,
      status: p.status,
      showPriceInShowcase: p.showPriceInShowcase ?? true,
      // ... 其他字段
    });

    // 2. 创建产品图片（替换旧 URL 为新 R2 URL）
    for (const img of p.images) {
      const newUrl = urlMap.get(img.url) || img.url;
      await db.insert(schema.productImages).values({
        productId: p.id,
        url: newUrl,
        alt: img.alt,
        sortOrder: img.sortOrder,
      });
    }

    // 3. 创建产品翻译
    for (const t of p.translations) {
      await db.insert(schema.productTranslations).values({
        productId: p.id,
        locale: t.locale,
        description: t.description,
        brewingGuide: t.brewingGuide,
      });
    }
  }

  console.log(`导入 ${products.length} 条产品数据`);
}
```

3. **首页配置、导航、SEO、网站设置**：在后台手动配置（量少，手动更稳）

### 9.3 迁移期间对网站的影响

| 时间点 | 老版状态 | 新版状态 | 客户感受 |
|:-----|:-----|:-----|:-----|
| 导出数据阶段 | 正常运行 | 尚未上线 | 无影响 |
| 导入数据阶段 | 正常运行 | 尚未上线 | 无影响 |
| 验证阶段 | 正常运行 | 测试域名可预览 | 无影响 |
| 切换 DNS 到新版 | **停止更新**（只读模式） | **正式上线** | 客户访问自动切到新版（DNS 生效 5-30 分钟） |
| 切换后观察期 | 保留 24-48 小时备用 | 正式上线 | 如有问题切回老版（改 DNS 回原 IP） |

### 9.4 数据安全保证

- **不丢数据**：导出前对老数据库做一次 Neon 时间点恢复（保留快照），即使迁移脚本出错，老数据完好无损
- **可验证**：每一步都有校验脚本，对比新旧数据条数
- **可回退**：迁移后如果发现问题，DNS 切回老版，新版数据库重来
- **无覆盖风险**：导入脚本使用 `INSERT`（新写入），不会覆盖已有数据；如果数据已存在，脚本报错停止
